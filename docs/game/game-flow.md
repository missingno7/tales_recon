# Game flow: startup, the 30 days, the office, the map, the rival

What the recovered code shows this part of the game doing. Names are the ones in `recovery/names.json` (applied in src/); mechanical names (`ovNN_F_XXXX`, `G_h01_XXXX`) are things not yet understood well enough to name. First written from the 2026-10-18 naming review.

## Startup, display, and resources

The resident entry calls the overlay entry `run_game_session`, which initializes audio/video, runs the adventure, and shuts the display and devices down. `initialize_av` opens graphics, intuition, and layers libraries; allocates the two screen bitmaps and a scratch bitmap; builds the display view and color map; opens Topaz; and starts audio/input. `switch_display_buffer` flips the active screen bitmap at each display update. `shutdown_av` restores preferences and the Workbench, releases display resources, closes the current archive and libraries, and shuts down audio/input. These are Amiga display lifecycle effects, not game rules.

The game reads indexed `.arc` resources. `arc_read_index`, `read_le16`, and `read_le32` read an index count and little-endian offsets. `arc_load_locations` opens `DT1:loc.arc` and parses location records; `arc_load_treasures` opens `DT1:loot.arc`, assigns non-duplicate treasure ids to locations, and reads each treasure's numeric value. The source establishes the fields it parses and uses, but not the meaning of every field in the location record. The text copied into the record and the remaining unused numeric field stay unnamed here.

Before difficulty selection, `play_game_startup_sequence` loads and plays a startup animation; fire input can skip the longer sequence. The animation assets and screen blits are visible in `load_opening_animation_assets`, `run_opening_animation_sequence`, and `expand_center_bitmap_to_screen`, but the characters or story represented by the animation records are not identified by code. `ui_choose_difficulty` shows "Easy Money," "Standard Wages," and "Hard Earned Cash" and stores difficulty values 0-2.

## Calendar, travel, and money

`game_run_adventure` is the main state machine. Day starts at 1 and the contest ends at day 30. The office is location/state 35; state 0 is the return-to-office settlement; state 36 opens the ordinary map; state 40 opens the matter-transmitter map; state 38 enters the Money Bin; and state 39 enters investments. Other selected values represent destinations. At the office, `office_select_destination` displays MONEY BIN, CONTROL CENTER, and INVESTMENTS and returns the selected branch to the main loop.

The map points use a 272-by-140 wraparound coordinate space. `calculate_travel_days` returns zero for the same location; otherwise it computes the shortest wrapped distance and converts it to one through three days. `map_select_destination` draws the map, moves a cursor from controller/keyboard input, identifies the nearest plotted location, and can show its name, description, treasure, value, and travel time through `map_show_location_details`. After Bombastium is found, the transmitter choice becomes available. The UI also shows current cash and day; ordinary location selection returns a destination index, while the office returns its special state.

Treasure collection adds the location's value to `total_money`. Returning to the office transfers that carried cash to the player's banked total and clears the carried amount. The final screen compares the player's banked cash with the rival's banked cash. The Money Bin scene (`money_bin_scene`) also has a bonus route: a particular animation/input path sets the transient result flag `money_bin_bonus_triggered`, returns success, and causes `game_run_adventure` to display the rare-coin message and add $1000. The main loop clears the flag before the next location encounter or office-return settlement, so the source establishes a per-scene result latch rather than a permanent once-per-game award flag.

## Rival and difficulty

The main loop uses the audio-completion flag while playing scene cues and waits for selected sounds to finish before continuing. `play_sound` and the reconstructed audio driver are a separate subsystem: `docs/audio-code-data.md` describes score/envelope bytes classified as DATA inside the CODE container, with some extents and contents still unresolved. As `docs/sdl3-port.md` explains, the port translates reconstructed assembly instruction-by-instruction to preserve the existing driver behavior. Those audio facts support how scenes synchronize; they do not identify the unknown opening-animation characters.

## Office and map interaction

`office_select_destination` waits for directional/fire input, highlights one of the three labeled office choices, and returns the Money Bin, Control Center, or Investments state. `initialize_office_menu_scene` prepares the office's background and moving menu records. `draw_office_choice_outline` draws an outline around one of eight numbered choices; its code shows the rectangle geometry, while it does not explain which narrative object each choice represents. `money_bin_scene` reads `DT1:mbin.arc`, presents an animated scene, and waits for fire input; it reports whether the bonus route was taken rather than directly updating `total_money`.

The map's cursor helper `map_move_cursor_from_input` maps eight direction values to movement, repeats movement while a direction is held, clamps the cursor to the map bounds, and handles fire. `draw_map_cursor_marker` paints the small location marker; `draw_map_option_outline` draws the rectangular option outline used by the map UI. When a location is selected, `map_show_location_details` reads the location and loot records and displays the location heading, description lines, treasure name, description, value, travel time, day, and cash. The game lets the player choose between destination and office controls from this screen.

## Data and unresolved names

The player and rival treasure tables are byte flags indexed by location; the reward slots contain a loot-record index and numeric value. The treasure id 9 maps to the Bombastium location used to unlock the transmitter. The map's location records also supply the coordinate words used for distance calculations. The global at `G_h01_4732` is an interior alias into the location-record storage used while checking treasure-id uniqueness, not an independent table, so it is not given a separate global name.

I left functions unnamed when their only clear role is a sequence of unnamed image/sprite records, short sound/dialogue branches, or an animation-state reset. In particular, `ov04_F_0926`, `ov04_F_0B50`, `ov04_F_0DBE`, `ov04_F_18A6`, `ov04_F_1A3A`, `ov04_F_1AA2`, `ov04_F_1D32`, `ov13_F_012E`, `ov13_F_0190`, and `ov14_F_03AE` stay mechanical. `ov04_F_0000` is a one-call forwarding wrapper and also stays mechanical. The fields `Location` text and `c` remain unnamed because the source does not establish their displayed role or use. `G_h01_46C8`, `G_h01_46DF`, and `G_h01_46F6` remain unnamed: the scoped code only uses a gate, clears a byte, and increments/decrements a counter, respectively, without establishing a semantic role.

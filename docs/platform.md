# Platform-layer contract

Static source contract for the later native port. This is an analysis artifact, not an implementation. Base: `dbe7e18`. No emulator was run.

Coverage snapshot: **88 runtime/OS members**, with **766 parsed C call sites**, and **37 absolute custom-chip/CIA register rows** across **20 functions with actual accesses**, plus one heuristic-only address candidate. The machine-readable companion [`platform.json`](../recovery/platform.json) carries every caller, source line, argument expression, result-use classification, glue/vector path, register access and evidence path.

## Proof categories and scope

- **Exact C**: accepted function code/data proof. Source may be cited as the behavior currently recovered.
- **Recovered ASM**: provenance-backed original assembly source.
- **Reconstructed ASM**: assembled, machine-checked mnemonic source; it has no original-source provenance.
- **Behaviorally reconstructed**: behavior supported by explicit tests/traces, with limits stated; never a byte/source match.
- **Unresolved**: no accepted source proof or behavior not established.
- Runtime member classification is **PINNED_RUNTIME** ABI evidence. It identifies a pinned member or OS vector; it does not establish exact original library object/version provenance.

The call-site arguments below are expressions at recovered callers; return-use labels describe what the C source does with the call result (assigned, tested, returned, or ignored), not a fixed runtime value. Full call-site roster is in JSON. Four rows have no lexical direct C call expression: `mul36`/`div36` are compiler-lowered integer operators, while `write`/`abort` are reached through runtime paths. The caller roster remains listed.

## OS and runtime calls

Each API entry names its AmigaOS vector (negative LVO from the library base) and decoded glue entry where applicable. An em dash means an inline/runtime helper or pinned C member with no OS LVO. The caller column lists every discovered caller and its proof category; `platform.json` gives source paths and exact line-level argument/result-use records.

### Grouped hardware behavior

- **Bitplanes / blitter:** exact-C `resident_F_33E6` waits for `DMACONR` bit 6 to clear, configures the BLTCON/mask/modulo/pointer registers, starts each blit via `BLTSIZE`, and writes the recorded DMACON values around the operation. `resident_F_4676` separately samples VPOSR; the downstream meaning of its stored value remains unresolved.
- **Display Copper / palette:** no direct Copper-list register store was found in the scanned absolute operands. Display is driven through graphics.library view, viewport, color-map and blit calls; game palette/Copper data is constructed and loaded through those paths.
- **Paula audio and interrupts:** reconstructed-ASM driver code addresses AUD0–AUD3 pointer/length/period/volume banks. Per-channel handlers check DMACONR channel bits, queue the next block, update DMA and acknowledge INTREQ. INTENA enables/disables channel interrupts; ADKCON is cleared during setup. This evidence is reconstructed assembly, not original-source provenance.
- **Joystick / mouse / keyboard:** exact-C `resident_F_4376` reads JOY1DAT and CIAA PRA (`$BFE0FE`, alias `$BFE001`); JOY1DAT bit pairs are combined into the port-2 eight-direction map, and CIA PRA bit 7 is inverted as active-low fire. Keyboard input comes separately through `input.device` raw events and the key ring.
- **CIA timers / VBlank:** no absolute CIA timer register access was found. VBlank is registered through Exec AddIntServer, not by writing a custom interrupt register directly.

A heuristic-only candidate is kept separate: exact-C `resident_F_4F62` assigns `$BFE0FE` to a local but never dereferences it. It is **not** an additional hardware read. See `hardware_address_only_candidates` in JSON.

## Timing and interrupt model

- **Frame tick:** `resident_F_615E` (reconstructed ASM; [`src/recovered/asm-reconstructed/resident_frameless_615E.asm`](../src/recovered/asm-reconstructed/resident_frameless_615E.asm)) is installed with Exec `AddIntServer(5, ...)`. Custom source 5 is VERTB / vertical blank (CPU interrupt level 3). Each invocation increments `G_h01_B1EC`, establishes the game A4 data base, calls the per-frame callback, then invokes `resident_F_58BC` for frame-based audio state. The registration/setup caller is exact C `resident_F_50E8`.
- **Paula IRQs:** `SetIntVector` sources 7–10 install the four channel handlers ``resident_F_55D6`, `resident_F_5646`, `resident_F_56B6`, `resident_F_5726`` (reconstructed ASM; source files under `src/recovered/asm-reconstructed/`). These sources map to AUD0–AUD3 at CPU interrupt level 4. Each handler advances channel state, provides the next sample block, stops on a terminator, and acknowledges its request.
- **Tick wait:** exact-C `resident_F_4F40` ([`src/recovered/resident/resident_F_4F40.c`](../src/recovered/resident/resident_F_4F40.c)) spins while `G_h01_B396 == G_h01_B1EC`, then copies the new tick. Its accepted caller is teardown `resident_F_53E6`; it is not evidence that the entire game loop is this wait.
- **Beam sample:** exact-C `resident_F_4676` ([`src/recovered/resident/resident_F_4676.c`](../src/recovered/resident/resident_F_4676.c)) reads VPOSR and adds the current tick before storing to `G_h01_3AB8`. No accepted consumer of that word is known, so its purpose remains unresolved.
- **Other waits:** DOS `Delay` calls occur at many callers; preserve their observed tick counts. Gameplay also busy-polls state such as the audio-completion flag in `game_run_adventure`; preserve the release frame. No CIA timer loop was found.

### Port must provide

- Advance exactly one game tick per host frame and preserve callback order: tick increment → game callback → per-frame audio update.
- Deliver queued input with the same frame ordering and edge behavior; preserve VBlank/keyboard state interactions.
- Preserve Paula score progression, sample block boundaries, per-channel timers, envelope/vibrato/pitch changes, stop/loop behavior and audio-completion frame. Compare both game-state traces and output audio buffers.
- Match DOS Delay and other observed wait release frames. Host refresh rate may differ; frame count and trace alignment are the contract.

### Established container behavior and limits

`.arc` reads use DOS `Open`, `Seek`, and `Read` through the named loaders and the resident indexed-resource routines. [`formats/arc.md`](../formats/arc.md) documents the little-endian count/offset table, 16-byte headers, supported record branches (five-plane RLE kinds 1/2, LZW kind 4, packed ADPCM kind 5, and text/binary kinds 3/6), with per-kind limits. The supplied kind-5 records documented in `formats/arc.md` occur in the `.as` files rather than these `.arc` files. Some RLE reads refill a 1024-byte stream buffer and can pass a record span; the source behavior is retained and not silently normalized.

For `DT1:dt1.as`, accepted exact C `resident_F_50E8` opens the file and calls exact-C `resident_F_2816`. That helper seeks to zero, reads a little-endian u16 count, rejects counts above 104, then reads that many little-endian u32 offsets into `G_h01_A7EE`. This proves an index read, not the record headers or payload meaning. It corrects the stale statement in [`formats/as.md`](../formats/as.md) that no matched C names or reads `dt1.as`; the measured record structure there remains an independent structural inference, while payload kinds/inner codecs remain **UNKNOWN**. `DT2:dt2.as` is only opened/stored by matched `resident_F_0FDE`; no matched read is established.

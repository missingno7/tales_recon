# VISION — DuckTales Amiga Reconstruction

## Purpose

This project exists to reconstruct the original Amiga DuckTales game project in a form that is:

- readable;
- explainable;
- evidence-driven;
- independently buildable;
- structurally faithful to the historical executable;
- useful as the authoritative foundation for a future source port.

The reconstruction is not merely a decompilation exercise.

The goal is to recover the software project behind the binary.

---

## The long-term picture

We want to move from:

```text
original Amiga disks
        ↓
opaque historical executable
```

to:

```text
readable reconstructed project
        ↓
historically faithful build
        ↓
understood game architecture
        ↓
clean portable source port
```

The reconstructed historical project and the future source port are two different products.

The historical reconstruction is the truth layer.

The source port is the portability layer built on top of that truth.

---

# What success looks like

At the end of the reconstruction effort, a developer should be able to open the repository and understand:

- how the game boots;
- how the resident core is structured;
- how the Amiga HUNK executable is laid out;
- how the overlay system is organised;
- what each overlay does;
- which code belongs to the game;
- which code belongs to Manx/Aztec C runtime or other libraries;
- which portions were written in C;
- which portions were written in 68k assembly;
- how the game stores its global state;
- how its important data structures are laid out;
- which assets each subsystem consumes;
- how disk files map to game systems;
- how the executable is linked;
- which parts of the reconstruction are proven;
- which names and structures are reconstructed interpretations;
- what uncertainty remains.

The project should feel like a recovered source repository, not like an annotated disassembly.

---

# Historical reconstruction first

The original game is not just a collection of functions.

It is a historical software system with:

```text
filesystem structure
startup sequence
resident executable
CODE / DATA / BSS hunks
overlay tree
runtime libraries
compiler conventions
asset containers
global data model
subsystems
hardware-specific code
```

We want to recover all of these.

A function-by-function decompilation that ignores the original build topology is not enough.

A modern reimplementation that happens to behave similarly is not enough.

A source port written independently from screenshots is not enough.

The reconstruction must explain how the original program itself was built and organised.

---

# The original executable is an oracle

The original binary is never treated as source code.

It is evidence.

We use it to answer questions such as:

```text
Did this function compile correctly?
Did this data layout match?
Did this relocation target match?
Did this overlay contain the expected contribution?
Did the linker naturally produce the expected structure?
```

The original executable should eventually disappear from the normal build path.

A normal reconstruction build must use:

```text
reconstructed source
+
pinned historical dependencies
+
pinned toolchain
+
original non-code game assets where legally/user-supplied appropriate
```

The original executable remains only a verification fixture.

---

# Preserve the historical architecture

The game already tells us important things about its original architecture.

The executable preserves:

- a resident/root program;
- CODE, DATA and BSS separation;
- a real Amiga overlay structure;
- thirteen overlay modules.

These boundaries are valuable historical evidence.

We should not throw them away early merely because a modern machine no longer needs overlays.

During reconstruction, the overlay architecture is part of the specification.

Later, the source port may flatten or redesign it.

---

# Recover meaning, not just syntax

A mechanical disassembly can tell us:

```asm
move.w  18(a0),d0
```

A reconstruction should eventually tell us something closer to:

```c
score = portfolio->value;
```

or:

```asm
move.w  Portfolio_Value(a0),d0
```

when the evidence supports that interpretation.

The goal is not merely to assign nice names.

Every semantic name must have a chain of evidence behind it.

We distinguish between:

```text
historical fact
reconstructed semantic meaning
plausible interpretation
unknown
```

We never pretend our reconstructed labels were necessarily the original programmer's labels.

---

# Recover C as C

If a region was generated by Manx Aztec C, our preferred final representation is C.

The historical compiler should become an oracle for that recovery.

The workflow is:

```text
original machine code
        ↓
understand semantics
        ↓
write candidate historical-style C
        ↓
compile with matching toolchain
        ↓
compare generated code
```

Matching code generation gives strong evidence that the recovered C has the right structure.

It does not prove whitespace, comments, macro spelling or original variable names.

Those are separate questions.

---

# Recover assembly as assembly

If a region is shown to be hand-written 68k assembly, preserve it as assembly.

Examples may include:

- blitter kernels;
- copper manipulation;
- interrupts;
- graphics inner loops;
- audio routines;
- memory copy/decompression code;
- hardware setup.

The reconstruction should not force one source language onto the whole game.

The recovered project may naturally be mixed C and assembly.

---

# Recover the data model

Readable game code requires readable data.

The reconstruction should recover:

- global variables;
- persistent game state;
- structs;
- arrays;
- tables;
- pointer tables;
- asset descriptors;
- overlay state;
- system handles;
- gameplay records.

A source tree where logic is readable but all state remains `data_base + 0x1834` is not complete.

The final reconstruction should make relationships between systems and data visible.

At the same time, historical layout must be preserved.

Readability must not silently change offsets or ownership.

---

# Asset archaeology is part of understanding the game

The game uses a substantial set of external data files.

These are part of the software architecture.

We should understand formats such as:

```text
*.arc
dt1.as
dt2.as
```

well enough to know:

- what content they hold;
- which overlay/system consumes them;
- how records are indexed;
- whether they are compressed;
- how graphics/maps/text/audio are represented.

Asset reverse engineering is not the same task as executable reconstruction, but the two inform each other.

---

# Historical fidelity has levels

Not all recovered information has the same certainty.

We explicitly distinguish:

```text
behaviour understood
semantic source recovered
machine code matched
data layout matched
HUNK content matched
relocations matched
overlay node reproduced
link layout reproduced
whole executable matched
```

A lower proof level must never be presented as a higher one.

For example:

```text
same behaviour
```

does not mean:

```text
same machine code
```

and:

```text
same machine code
```

does not mean:

```text
same object/HUNK/link structure
```

This precision is essential to keeping the project honest.

---

# Natural layout matters

Historical reconstruction is strongest when addresses and layout emerge naturally.

The project must avoid becoming a set of individually placed fragments.

The desired model is:

```text
source order
+
module ownership
+
object order
+
compiler / assembler
+
linker
        ↓
historical layout
```

not:

```text
put this function at original address X
put this data block at original address Y
patch the rest later
```

Temporary placement experiments are allowed as research.

They are not completion.

---

# Runtime libraries are not game code

A major objective is to identify and remove known runtime/library code from the game-recovery denominator.

If the executable contains Manx/Aztec runtime code, overlay support, math helpers or system wrappers that can be sourced from the correct historical distribution, those should be treated as dependencies.

We should recover what was actually authored for the game.

We should not spend months decompiling a historical compiler library that already exists.

---

# The reconstruction should become self-contained

Over time, normal development should require less and less archaeological machinery.

Initially we may need:

- original disks;
- disassemblers;
- WinUAE;
- runtime tracing;
- experimental compilers.

Eventually the project should build from source with a documented toolchain.

The original binary should be required only for validation.

A future developer should be able to read the reconstructed project without understanding the reverse-engineering workbench.

---

# The source port comes after understanding

Once the historical reconstruction is mature, it becomes possible to build a modern source port without guessing.

The source port can then deliberately replace platform-specific layers:

```text
AmigaOS filesystem       -> portable filesystem
Amiga input              -> SDL / native input
blitter/copper renderer  -> modern renderer
Amiga audio              -> portable audio backend
overlay loading          -> modern module/static layout
timing/interrupt model   -> portable game loop
```

The source port should preserve the game model recovered from the original.

It should not invent a second independent implementation of the game's rules.

---

# Separation of layers

The desired long-term relationship is:

```text
historical evidence
        ↓
historical reconstruction
        ↓
semantic game model
        ↓
portable platform layer
        ↓
modern source port
        ↓
optional enhancements
```

Each layer has a different job.

## Historical evidence

Answers:

> What existed?

## Historical reconstruction

Answers:

> How was the original game implemented?

## Semantic game model

Answers:

> What are the actual systems, structures and rules?

## Source port

Answers:

> How do we run those systems on modern platforms?

## Enhancements

Answers:

> What can we improve without confusing improvements with recovered history?

---

# No carrier architecture in the final project

Reverse-engineering scaffolding is temporary.

Breakpoints, binary hooks, emulation bridges and runtime patches may be useful while discovering behaviour.

They must not become the reconstructed architecture.

The final historical project should look like source code that could be built normally.

The future source port should likewise run without an original executable or emulator.

---

# Windows-first reconstruction workflow

The practical development experience should remain modern and automatable.

Prefer doing on Windows:

```text
source editing
HUNK parsing
68k static analysis
compiler orchestration
assembly
linking
byte comparison
relocation comparison
progress generation
```

Use WinUAE as:

```text
runtime microscope
behaviour oracle
historical Amiga-tool runner where unavoidable
```

not as the normal development environment.

If a historical compiler only runs under AmigaOS, automate it.

Agents should be able to iterate without manually clicking through Workbench.

---

# Documentation is part of the reconstruction

The project must explain itself.

Maintain:

```text
docs/vision.md
docs/project-brief.md
docs/progress.json
docs/blockers.json
docs/modules.json
docs/symbols.json
docs/data-layout.json
docs/toolchain.json
```

The documents must distinguish:

- measured fact;
- historical provenance;
- semantic interpretation;
- current hypothesis;
- unresolved question.

A future contributor should not have to rediscover why a decision was made.

---

# The first major milestone

The first milestone is not "game runs".

The original game already runs.

The first milestone is:

> One complete historical overlay has been reconstructed as readable C/ASM, compiled with the selected historical-compatible toolchain, and reproduced through the normal overlay build path with all relevant code/data/relocation relationships verified.

This proves the methodology.

Only then scale aggressively.

---

# The second major milestone

The resident core and all overlay modules have readable ownership maps.

At this point we know:

```text
what is game code
what is runtime code
what is C
what is ASM
what data belongs to which system
what remains unknown
```

This is the point where the executable stops being opaque.

---

# The historical end state

The ideal historical reconstruction is:

```text
complete readable source tree
+
understood C/ASM ownership
+
typed/named data model
+
documented asset formats
+
preserved overlay architecture
+
pinned toolchain/dependencies
+
natural historical build
+
localized explicit remaining differences
```

If whole-file binary identity is possible, pursue it.

If some metadata cannot be reproduced, isolate the exact reason rather than weakening the rest of the reconstruction.

---

# The source-port end state

The later source port should be:

```text
independent of original executable
independent of WinUAE
independent of AmigaOS
portable
readable
maintainable
faithful by default
```

while remaining traceable back to the reconstructed original systems.

Enhancements can then be built confidently because we know which behaviour is original and which behaviour is new.

---

# Final principle

The goal is not to make DuckTales run on another machine as quickly as possible.

The goal is to recover enough of the original project that we genuinely understand what was built, how it was structured, and how its systems worked.

Then the source port becomes an engineering project instead of a guessing project.

> Recover the original architecture first. Port the recovered architecture second.
